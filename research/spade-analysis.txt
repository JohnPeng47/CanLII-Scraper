## SPADE: Synthesizing Data Quality Assertions for LLM Pipelines — Detailed Analysis

**Paper**: arXiv:2401.03038v2 (March 2024)
**Authors**: Shreya Shankar et al. (UC Berkeley, HKUST, LangChain, Columbia University)

---

### 1. Problem Statement

LLMs are increasingly deployed as data pipelines — systems that repeatedly process or generate text at scale (e.g., summarizing documents, generating personalized recommendations, drafting emails). These pipelines suffer from frequent, unpredictable errors: LLMs ignore instructions, produce wrong output formats, or hallucinate facts seemingly at random.

The standard mitigation is **data quality assertions** — boolean checks applied to LLM outputs at runtime to flag bad results. The problem is that **determining which assertions to write is itself a hard, open problem**. Developers struggle because:

- LLM failure modes are hard to predict in advance.
- Writing assertion functions (Python or LLM-call-based) is time-consuming and requires software engineering skill that many pipeline developers lack.
- When there are too many or non-informative assertions, developers become overwhelmed monitoring the results.
- Existing work on data quality for traditional ML pipelines operates on structured records in bulk and does not transfer to the free-form, unstructured LLM output setting.

The central research question: **Can we identify a minimal, accurate set of data quality assertions for LLM pipelines with as little developer effort as possible?**

The insight motivating the approach: developers implicitly embed their quality requirements into the prompt itself, over time, through iterative edits (prompt deltas). These edits are a latent signal that has never been exploited for assertion generation.

---

### 2. Key Technical Approach — How SPADE Synthesizes Assertions

SPADE (System for Prompt Analysis and Delta-Based Evaluation) has two sequential components.

#### Component 1: Candidate Assertion Generation via Prompt Deltas

**The core insight** is that when developers fix an LLM failure mode, they add an instruction to the prompt (e.g., "Don't reference race in your answer"). Each such addition is an implicit data quality requirement, and therefore a candidate assertion criterion.

**Step 1 — Taxonomy Construction.** The authors analyzed 19 real LangChain pipelines with 3–11 historical prompt versions each. Through open/axial coding (4 iterations, 2 authors), they produced a taxonomy of prompt deltas:

- **Structural** (35% of deltas): Response Format Instruction, Example Demonstration, Prompt Clarification
- **Content-Based** (65%): Workflow Description, Data Integration, Quantity Instruction, Inclusion Instruction, Exclusion Instruction, Qualitative Criteria

GPT-4 was validated to classify prompt deltas against this taxonomy at an F1 of 0.8135.

**Step 2 — Two-step LLM prompting per delta.** For each prompt delta ΔPᵢ (the diff between consecutive prompt versions):
1. GPT-4 is prompted to generate natural language descriptions of assertion criteria aligned with the taxonomy categories.
2. GPT-4 is then prompted to synthesize Python assertion functions implementing those criteria.

Crucially, SPADE analyzes **every delta** (not just the final prompt version) because: (a) developers often delete instructions from prompts to reduce token costs while still expecting compliance; (b) complex prompts lead to missed assertions if only one version is analyzed; (c) prompts contain ambiguities that imply multiple evaluation approaches.

The synthesized Python functions can use standard libraries or make LLM calls (`ask_llm(prompt, response, question)`) for qualitative criteria. For vague criteria like "check for conciseness," the LLM may generate multiple candidate functions (word count check, sentence count check, LLM-call check). This produces a multiset of candidate functions F = {f₁, ..., fₘ}, often 50+ for a handful of prompt versions.

#### Component 2: Filtering via Integer Linear Programming + Subsumption

Given the candidate set F and a small labeled sample E' of LLM input-output pairs (with developer labels of good=1 / bad=0), SPADE selects a minimal subset F' ⊆ F.

**Key metrics:**
- **Coverage(F')**: fraction of actual failures correctly flagged by F'.
- **False Failure Rate (FFR)(F')**: fraction of actually-good examples incorrectly flagged as failures.

A pipeline execution eᵢ is deemed a failure by F' if *any* assertion in F' fails (conjunction semantics).

**The optimization problem:**

minimize |F'|  subject to: Coverage(F') ≥ α, FFR(F') ≤ τ

This is proven **NP-hard** (reducible to Set Cover when τ=0, α=1) but tractable in practice since the ILP has at most tens of assertions and ~75 examples (thousands of variables), solved in under 1 second using the PuLP/CBC solver. This variant is called **SPADE_cov**.

**The subsumption extension (SPADE_sub):** When E' is small and not representative of all failure modes, SPADE_cov may exclude assertions that would catch unseen failure types — because those types don't appear in E'. To address this, the authors introduce **assertion subsumption**: a set S subsumes function f if every failure caught by f is also caught by some function in S (i.e., f adds no new coverage).

The modified ILP minimizes |F'| + |G| where G is the set of functions in F \ F' that are *not* subsumed by F'. This pushes the solver to prefer solutions where excluded assertions are at least logically implied by included ones.

**Determining subsumption:** For pure Python functions, static analysis could apply. In practice, SPADE uses GPT-4 to identify subsumption pairs in two LLM calls (one to list candidates, one to format them). Heuristics prune the search: if example data shows fᵢ passes but fⱼ fails for some eᵢ, then fᵢ cannot subsume fⱼ; FFR bounds further prune. Transitivity is applied. Average precision of subsumption detection across 9 pipelines: **0.82**.

**Zero-data case:** When no labeled examples are available, the ILP reduces to a topological sort on the subsumption DAG — select all "root" nodes (those with no incoming edges), which are not subsumed by anything. This is in PTIME.

### 3. System Design

SPADE is deployed as an integration within **LangSmith**, LangChain's LLM pipeline hub.

**User interface:** A Streamlit app (https://spade-beta.streamlit.app) where developers can:
- Paste a prompt template or point to a LangChain Hub prompt (which stores version history via git-style commits).
- SPADE visualizes which taxonomy categories appear in each delta.
- Displays candidate Python assertion functions.
- Allows download as a `.py` file.

**Runtime flow:**
1. Developer commits a new prompt version → SPADE reads the delta history.
2. GPT-4 categorizes each delta and generates candidate assertion criteria.
3. GPT-4 synthesizes Python functions for each criterion.
4. If labeled examples E' are available, SPADE runs the ILP solver (PuLP/CBC) to select F'.
5. Selected assertions are embedded in the pipeline for runtime monitoring.

**Assertion function signature:** All generated functions have the form:
```python
async def assert_X(example: dict, prompt: str, response: str) -> bool:
    ...
```
They may call `ask_llm(prompt, response, question)` for LLM-based checks or use deterministic Python logic (regex, substring search, JSON parsing, etc.).

**Cost of the ILP:** Runtimes ranged from 0.10–0.63 seconds for SPADE_cov and 0.12–1.20 seconds for SPADE_sub across the nine pipelines. The fashion pipeline (16 prompt versions, 106 candidate assertions) was the largest at 1.197 seconds for SPADE_sub.

### 4. Evaluation Results

**Setup:** 9 real-world LLM pipelines. 8 from LangChain Hub (open-sourced), 1 proprietary fashion pipeline (deployed in production for tens of thousands of daily runs). Each has ~75 labeled examples (mean ~34 bad, ~40 good). Thresholds: α = 0.6 (cover at least 60% of failures), τ = 0.25 (false failure rate ≤ 25%).

Three methods compared:
- **Baseline**: Keep all candidates where individual FFR ≤ τ.
- **SPADE_cov**: ILP over coverage + FFR constraints.
- **SPADE_sub**: ILP with subsumption penalty for excluded-but-unsubsumed functions.

**Key results (Table 4):**

| Pipeline | # Candidates | Baseline FFR | SPADE_sub FFR | Baseline % selected | SPADE_sub % selected |
|---|---|---|---|---|---|
| fashion | 106 | 0.878 (FAIL) | 0.224 (pass) | 63.2% | 37.7% |
| finance | 47 | 0.667 (FAIL) | 0.208 (pass) | 78.7% | 55.3% |
| lecturesummaries | 70 | 0.528 (FAIL) | 0.194 (pass) | 45.7% | 34.3% |
| negotiation | 50 | 0.444 (FAIL) | 0.185 (pass) | 40% | 34% |
| codereviews | 44 | 0.117 (pass) | 0.117 (pass) | 45.6% | 34.1% |

**Summary statistics:**
- Baseline violates the FFR constraint in **4 of 9 pipelines**. Neither SPADE variant ever violates it.
- SPADE_sub selects **~14% fewer assertions** than baseline on average.
- SPADE_sub reduces FFR by **~21% relative to baseline**.
- SPADE_cov selects the fewest assertions overall (sometimes just 1–4) but leaves ~44% of excluded functions unsubsumed — meaning it discards potentially useful assertions simply because the failure types they catch are absent from the small E'.
- SPADE_sub is less sensitive to α than SPADE_cov, since subsumption provides a structural guarantee even when labeled failures are sparse.

**The fashion/lecturesummaries case** illustrates why individual FFR filtering is insufficient: with 67 and 32 baseline-selected assertions respectively, conjunctive semantics drives total FFR to 88% and 53%, even though each individual assertion is below the 25% threshold. The FFR upper bound grows additively (Equation 2 in the paper).

**Deployment evidence:** Over 2,000 runs of the Streamlit app, spanning health, IT, finance, education, cooking, project management, customer support, sports/entertainment, marketing, and others. Average of 3.3 assertions generated per run (min 1, max 10). 48 users downloaded assertions as Python files. The proprietary fashion pipeline has SPADE assertions running in production at tens of thousands of daily LLM calls.

### 5. Limitations

The paper is explicit about its limitations:

**a) LLM quality for assertion generation.** GPT-4 struggles with generic exclusion instructions (e.g., "avoid unrelated ideas") — it generates functions that do keyword matching for phrases like "unrelated" instead of semantically checking relevance. This produces low-quality assertions for vague criteria. Fixing this may require fine-tuned specialized models.

**b) Labeled data is hard to collect.** The ~75-example E' datasets were mostly synthetically generated (via ChatGPT) and manually labeled by the authors. In practice, acquiring and labeling real pipeline outputs at this scale is non-trivial. The paper notes developers would need either passive collection via API wrappers or active feedback mechanisms.

**c) Small E' leads to SPADE_cov over-pruning.** With limited labeled failures, SPADE_cov aggressively discards assertions that would catch failure types not yet observed. On average, 44% of excluded assertions in SPADE_cov are not subsumed, meaning they are genuinely different assertions that could be useful in production. SPADE_sub mitigates this but does not fully solve it.

**d) Single-step pipelines only.** The entire framework assumes a single prompt template executed repeatedly. Multi-step pipelines (RAG pipelines, chains with tool use, human-in-the-loop workflows) are not addressed. Extension to multi-step pipelines — including assertions on retrieved context, intermediate outputs, or tool calls — is identified as future work.

**e) Subsumption detection precision, not recall.** The authors explicitly don't evaluate recall of subsumption detection (whether GPT-4 found *all* true subsumption pairs) because labeling all possible pairs at scale is impractical. If subsumptions are missed, SPADE_sub may still include redundant assertions.

**f) Threshold sensitivity.** The α and τ thresholds must be set by developers, and if the ILP is infeasible (e.g., α too high with too few good assertions), developers must tune them by binary search. No automated mechanism for threshold recommendation is provided.

**g) Prompt version history required.** The approach requires that developers have been maintaining versioned prompt histories. For developers who haven't committed prompt history, only the final prompt version is available, yielding fewer and potentially weaker candidates.

**h) No human-in-the-loop interface.** The system currently outputs assertions for human review, but there is no interactive interface where developers can iteratively refine the α/τ tradeoffs, label examples on-the-fly, or prioritize certain types of assertions.

### 6. Relation to the Broader LLM Pipeline Quality Field

SPADE sits at the intersection of several research lines:

**vs. Manual assertion specification systems (Guardrails AI, LlamaIndex, LangChain):** These systems provide mechanisms to *embed* assertions but require developers to write them. SPADE *generates* the assertions automatically. SPADE is complementary: it could populate these systems.

**vs. LLM evaluation frameworks (EvalLM, ARES, RAGAS):** These focus on evaluating LLM outputs against standardized metrics (factuality, coherence, ROUGE, etc.) or human scorecards. SPADE is task-specific — it generates assertions tailored to a specific pipeline's requirements as expressed in its prompt history. SPADE's assertions are lower-level checks (inclusion/exclusion/format) rather than holistic quality scores.

**vs. DSPy Assertions:** DSPy Assertions (concurrent work, Singhvi et al. 2023) use assertions as computational constraints during LLM self-refinement — they trigger backtracking or retry when assertions fail. SPADE focuses on the *selection and synthesis* problem of which assertions to write in the first place, and uses them for monitoring rather than self-refinement. The two approaches are complementary.

**vs. Model assertions for traditional ML (Kang et al. 2020):** Traditional model assertions require human specification and large datasets. SPADE leverages the LLM itself to generate and evaluate assertions with minimal data.

**vs. Data validation for structured ML pipelines (TFX Data Validation, Breck et al.):** Traditional validation operates on structured feature distributions and schema checks at the dataset level. LLM outputs are unstructured and per-record, requiring assertion logic that can include LLM calls — a fundamentally different regime.

**vs. LLMs for software testing (unit test generation):** SPADE uses LLMs to generate test-like functions for LLM pipeline outputs, but the "system under test" is itself an LLM — creating a meta-level challenge where the assertion generator and the thing being tested are both probabilistic.

**Broader contribution to MLOps:** SPADE addresses the "last mile" problem of LLM deployment — how to catch errors at runtime, post-deployment, at scale. It connects prompt engineering (the development-time activity) to production monitoring (the operational activity) through the shared artifact of the prompt version history. This framing — prompt history as an implicit specification of data quality requirements — is a novel contribution to the LLM operations literature.

**Deployment at scale:** Unlike most academic systems, SPADE has real-world validation: it is deployed within LangSmith and has generated assertions for 2,000+ pipelines across 10+ industries. The fashion pipeline runs assertions in production at tens of thousands of calls per day. This gives the paper unusual empirical grounding.
