## Detailed Analysis: "LLM-Powered Proactive Data Systems" (arXiv 2502.13016)

**Authors:** Sepanta Zeighami, Yiming Lin, Shreya Shankar, Aditya Parameswaran — UC Berkeley
**Published:** 18 February 2025 (IEEE TCDE Bulletin vision paper)

---

### 1. Problem Statement

The paper's central critique is that current LLM-augmented data systems are **reactive**: they treat LLM calls as opaque, black-box UDFs (user-defined functions) applied to monolithic user inputs and data exactly as provided. The system simply executes what it is told, without understanding the semantics of the operation, the structure of the data, or the user's actual underlying need.

The authors identify three specific failure modes of reactive systems, illustrated through a concrete running example — a UC Berkeley police misconduct document database containing millions of PDFs from 700 agencies:

- **Difficulties with the data.** Providing entire multi-hundred-page documents to an LLM causes errors (the "lost in the middle" problem). Naive RAG chunking doesn't help because it lacks semantic understanding of document structure. Reactive systems treat unstructured data as an indivisible monolith.

- **Difficulties with the operations.** Asking an LLM to extract dozens of fields simultaneously in a single prompt degrades accuracy. Reactive systems don't understand that operations can or should be decomposed. They treat the user-specified prompt as the only possible formulation.

- **Difficulties with user intent.** A query for "John Smith" will miss "J. Smith" or "John M. Smith." A reactive system faithfully executes the literal query but fails the user's actual goal — finding all mentions of a specific person. The user doesn't even know what they're missing.

The paper's thesis is that these limitations are structural, not incidental, and require a fundamentally different design philosophy.

---

### 2. Key Technical Approach

The paper proposes **proactive data systems**: systems that are granted agency — empowered by LLMs — to understand, rework, and optimize three things before and during execution:

1. **The operations** (what is being done)
2. **The data** (what it is operating on)
3. **The user's intent** (what the user actually needs)

Rather than mapping LLMs onto existing abstractions (UDFs, approximate query operators), proactive systems treat the LLM as an intelligent meta-layer that can plan, restructure, decompose, and interact. The system is no longer passive; it has initiative.

The approach is characterized by moving away from the "single-shot query-result paradigm" toward iterative, agentic, and feedback-driven processing.

---

### 3. Architecture and Framework Design

The paper organizes the proactive data system's capabilities into three axes, each with multiple concrete mechanisms:

#### Axis 1: Proactive Operation Understanding (Section 3)

**3.1 — How and where to introduce new operators:**

- **Decomposition into simpler LLM operations.** A prompt that extracts fields f1...fn is rewritten into n separate prompts, each targeting one field. LLMs are used to generate the rewrites themselves. This mirrors ideas in Text-to-SQL (e.g., CHASE-SQL) where decomposing schema matching into sub-tasks improves accuracy.

- **Leveraging non-LLM components.** Operations are split between LLM reasoning (e.g., identifying which cases involved settlements) and traditional SQL computation (e.g., computing the average settlement). The system decides which parts belong where, as implemented in their ZenDB system.

- **Leveraging reasoning or data feedback for reformulation.** Rather than using a single powerful model (like o1) to do one-shot reformulation, the system should learn from actual data runs which reformulations work better for which data characteristics. The paper explicitly flags this as an open problem requiring agentic approaches.

- **Calibrating LLM outputs.** For operations like severity scoring, LLMs often give non-discriminative or inconsistent outputs. Proactive systems address this by: selecting representative few-shot examples that cover the full output range; rewriting prompts to include explicit scoring criteria; constraining the output space (e.g., standardizing "CA" vs "California").

**3.2 — Assessing and improving performance with reformulation:**

- **LLM-as-evaluator for comparing formulations.** A sample of data is run under both the original and decomposed formulation. Since LLMs are better at evaluation than generation, an LLM judge compares which version is more accurate. This implements a "generate-fix and rewrite-verify" loop, as used in DocETL.

- **Deferring to cheaper LLMs for simple sub-tasks.** After decomposition, easy sub-tasks (e.g., extracting dates and locations) are routed to smaller, cheaper models; hard tasks (e.g., classifying misconduct type) go to more expensive models. The paper notes the optimization space is unbounded since decompositions are infinite and model/threshold assignments combinatorial.

- **Expensive predicate ordering with synthesized predicates.** Drawing on classical database query optimization (Hellerstein & Stonebraker 1993), the system can introduce new, cheaper intermediate predicates to filter documents before expensive LLM evaluation. E.g., first cheaply check whether a document contains any medical information before running the expensive "what were the medical impacts" extraction.

#### Axis 2: Proactive Data Understanding (Section 4)

**4.1 — Identifying semantic structure within a document:**

- **Leveraging implicit hierarchical structure.** Documents have implicit section hierarchies. The system uses formatting cues (headers, indentation) or an LLM to identify these, constructing a semantic tree (as in their ZenDB system). Queries are routed to the right granularity node — e.g., routing a question about medical impacts to the medical examiner report sub-section rather than the entire document. This outperforms both RAG and full-document approaches. The paper flags the challenge that the "right" semantic structure depends on the task: "location" in a police record might mean geographic address for one analyst and indoor/outdoor type for another.

- **Leveraging explicit structure.** Documents contain embedded tables, key-value pairs, and forms. Their TWIX tool automatically extracts these using a combination of visual and LLM inference, preserving contextual relationships to surrounding text.

**4.2 — Identifying cross-document relationships:**

- Documents about the same incident may be spread across multiple PDF files with no explicit linking. The system must cluster documents by incident. The paper notes that simple embedding + clustering fails due to length variation. LLM-based pairwise comparison is accurate but O(n²)-expensive. The proposed direction is to use LLMs to identify cheap blocking rules (e.g., non-overlapping date ranges → definitely different incidents) to make the comparison tractable.

- **Shared template identification.** Recognizing that many documents follow the same internal structure (e.g., all use-of-force reports have an internal affairs section) allows the system to scale extraction and to identify structural outliers (e.g., reports without an IA section signal the absence of disciplinary action).

**4.3 — Task-aware data pre-processing:**

The system must balance offline preprocessing (expensive materialized views) against full laziness (everything at query time). The proposed middle ground: identify semantically significant document sections that are likely useful across many future queries, and create lightweight index pointers to these sections without fully materializing extracted attributes. Full extraction happens on demand. For example: precompute and index all sections mentioning police officers (useful for most queries), but don't extract all officer attributes until the user specifies which ones they need.

#### Axis 3: Proactive User Understanding (Section 5)

**5.1 — Imprecision-aware processing:**

Rather than treating the user query as a complete and exact specification, the system considers multiple possible interpretations simultaneously — analogous to "possible worlds" semantics in probabilistic databases. Examples:

- Query for "John Smith" also searches for "J. Smith," "John M. Smith," etc.
- If a user has been consistently querying about a specific city, new queries without a location qualifier might be implicitly scoped to that city.
- If a query returns too many results, the system applies intelligent summarization rather than overwhelming the user.
- If a query returns zero results, the system can relax predicates or expand scope (e.g., to neighboring jurisdictions) and proactively tell the user what it found under relaxed conditions.

**5.2 — Leveraging user feedback:**

- The system can ask targeted follow-up questions at key decision points (e.g., when encountering "J. Smith" — "Should I treat partial name matches as the same person?"). The key design challenge is minimizing the burden: ask one generalizable clarifying question rather than many narrow ones.
- Feedback loops back to all three axes: user corrections can update operation rewrite rules (Section 3), data representations (Section 4), and semantic structure extraction. This is compared to but explicitly extended beyond query-by-example systems.

**5.3 — Verifying execution:**

Proactive systems make autonomous decisions (e.g., correcting names, routing to document sub-sections) that users must be able to audit. The system should provide execution traces showing what decisions were made, what corrections were applied, and which documents were flagged as anomalous. The open challenge is presenting a small, comprehensible explanation that conveys the same information as the full provenance trace.

### 4. Evaluation and Case Studies

This is a **vision/position paper**, not an empirical evaluation paper. There are no experiments, benchmarks, or quantitative comparisons in this paper itself. Instead, the paper grounds its claims in prior published work from the same research group:

- **ZenDB** (arXiv 2405.04674): Demonstrates that semantic hierarchy construction and sub-document routing outperforms both naive RAG and full-document LLM calls in terms of accuracy and cost for document analytics. Also demonstrates hybrid LLM + SQL pipelines for structured attribute extraction.

- **DocETL** (arXiv 2410.12189): Demonstrates agentic query rewriting and decomposition with LLM-based evaluation for complex document processing. Uses the "generate-fix and rewrite-verify" pattern. Applied to police misconduct documents and other complex document collections.

- **TWIX** (arXiv 2501.06659): Automatic extraction of structured components (tables, key-value pairs) from templatized documents using visual + LLM inference.

- **NUDGE** (arXiv 2409.02343): Lightweight non-parametric fine-tuning of embeddings for retrieval, applied to user-intent alignment.

- **Visualization intent inference** (CIKM 2024): Shows that inferring intent from conversation context and adapting responses accordingly outperforms single-shot query handling.

- **SPADE** (arXiv 2401.03038): Synthesizing assertions/test cases for LLM pipelines to detect where LLMs go wrong.

The police misconduct database at UC Berkeley (California Police Records Access Project) serves as the primary real-world application throughout.

### 5. Limitations

The paper identifies several open challenges, which also constitute its limitations:

**Computational cost of proactivity.** Decomposing operations and running multiple formulations on samples increases LLM calls significantly. The cost-accuracy tradeoff in a space of infinite possible decompositions, with different models at different confidence thresholds for each sub-task, is described as "a lot more complicated" than prior cascaded model work.

**Accuracy metrics for open-ended operations.** Classic approximate query processing assumed well-defined accuracy metrics. For open-ended generative tasks (e.g., "describe the misconduct"), there is no ground truth, making it hard to automatically evaluate which formulation is better. The paper flags this as unresolved.

**Task-dependent semantic structure.** The "right" semantic hierarchy for a document depends on what queries will be run. Building a single structure useful for all downstream tasks is an open problem.

**Scalability of cross-document clustering.** O(n²) LLM comparisons are infeasible at scale. Blocking rules help but need to be automatically identified, which is itself an LLM-assisted task — creating a bootstrapping challenge.

**Deciding when and what to ask users.** Automatically determining which clarifying questions are most valuable and when to ask them (without burdening users) is explicitly identified as an open research problem.

**Provenance and explanation.** Presenting a compact, user-comprehensible explanation of autonomous system decisions remains unsolved. The paper proposes using LLMs to verify summary explanations but doesn't offer a concrete solution.

**No quantitative evaluation in this paper.** Being a vision paper, it does not itself provide experiments comparing proactive against reactive systems. The empirical evidence is deferred to the cited companion papers, each of which addresses only one sub-problem.

**Scope of "data" types.** While the paper mentions images and video as motivating examples in the abstract and introduction, the technical sections focus almost entirely on text documents. The application of proactive principles to video and audio remains largely unexplored.

### 6. Relation to the Broader Field

The paper explicitly positions itself within and against several research traditions:

**Against the UDF/approximate query processing tradition.** Systems like LOTUS (Patel et al., arXiv 2407.11418) and others treat LLMs as expensive approximate UDFs to be optimized like any other operator. The paper argues this framing is fundamentally wrong because it ignores semantics.

**Against RAG orthodoxy.** Retrieval-Augmented Generation is treated as a reactive approach that chunks without understanding. The paper's semantic hierarchy approach is presented as RAG done right — with structural and semantic awareness rather than fixed-size chunking.

**Against Text-to-SQL single-shot orthodoxy.** The paper cites work showing that decomposing NL2SQL translation into sub-steps (schema matching, concept identification) outperforms one-shot translation — a proactive operation decomposition insight applied to a well-studied problem.

**Connection to probabilistic/possible-worlds databases.** The imprecision-aware processing section explicitly draws on the possible-worlds semantics literature (Suciu et al., "Probabilistic Databases") as a conceptual predecessor.

**Connection to classic query optimization.** Predicate ordering (Hellerstein & Stonebraker 1993, Raman et al. 1999) is directly imported, but extended: unlike classic expensive predicates (e.g., UDFs), the proactive system can synthesize new intermediate predicates that didn't exist in the original user query.

**Connection to HCI and predictive interaction.** The user feedback and intent-inference sections connect to Heer, Hellerstein & Kandel's "Predictive Interaction" work (CIDR 2015) and query-by-example systems.

**Connection to agentic AI.** The paper implicitly endorses agentic patterns (multi-step, self-correcting, feedback-driven) for data system design, connecting it to concurrent work on LLM agents, though the paper maintains a database systems framing throughout.

**Key differentiating claim.** The paper's most important intellectual contribution is the argument that treating LLMs as black-box UDFs is not merely suboptimal but is the wrong abstraction altogether. The value of LLMs is not just their ability to execute operations but their ability to understand, plan, decompose, and reason about operations — and data systems should exploit all of these capabilities, not just the execution capability. This is a clean, strong position that challenges the default framing of the entire LLM-for-data-management literature.

---

**Summary.** This is a well-argued vision paper from a Berkeley group with substantial supporting work in DocETL, ZenDB, and TWIX. Its primary contribution is a clean conceptual framework (the reactive vs. proactive distinction, the three-axis design space of operations/data/intent) rather than a new algorithm or system. Its strength is the coherence of the vision and its grounding in real deployed systems; its limitation is that the open problems it identifies are genuinely hard and not yet solved, making the paper a research agenda as much as a research contribution.
