## 1. Problem Statement

The core problem is the difficulty of building effective **semantic data processing pipelines** — systems where LLM calls replace traditional code in data processing operators (map, reduce, filter, groupby) applied to large collections of unstructured documents (PDFs, transcripts, emails, reports).

The authors identify three structural "gulfs" that obstruct effective use of these pipelines, framed via Norman's gulfs of execution and evaluation:

**Gulf of Comprehension (User ↔ Data):** Documents contain more information than humans can manually process. LLMs introduce unpredictable errors across a corpus that are difficult to track at scale. Users lack bandwidth for sensemaking.

**Gulf of Specification (User ↔ Pipeline):** Users must discover their analytical intent through exploration, but expressing that intent as precise LLM prompts requires detailed, data-specific language. Intent often only crystallizes after seeing LLM outputs, creating a circular dependency. Prompts need to be data-specific but users don't fully understand their data yet.

**Gulf of Generalization (Pipeline ↔ Data):** Even a well-specified pipeline fails to generalize uniformly across a heterogeneous document corpus. LLMs struggle with long documents ("lost in the middle"), complex multi-objective operations, and edge cases. Complex tasks require decomposition into multiple LLM calls rather than a single operation.

The authors observe a "Three I's" workflow that users naturally follow — Initialize pipelines, Inspect outputs, Improve pipelines — but current systems provide almost no structured support for the outer human-centered loop of discovery and refinement, focusing instead on the inner computational loop (cost and accuracy optimization).

## 2. Key Technical Approach and UI/UX Design Decisions

DocWrangler is a **mixed-initiative IDE** built on top of DocETL as its backend execution engine. The design is organized around five goals:

- **D1** — Scaffold Pipeline Initialization
- **D2** — Facilitate Efficient Data Inspection and Notetaking
- **D3** — Guide Pipeline Improvement
- **D4** — Maintain End-to-End Observability
- **D5** — Minimize Context Switching

### Core Interface Layout

The unified workspace has three panes:
- **Left sidebar:** File browser and notes viewer (persistent notes across runs)
- **Center:** Notebook-style pipeline editor with operation cards
- **Right:** Spreadsheet-style dataset viewer with auto-generated visualizations

### Three Novel Features

**Feature A — In-Situ User Notes (addresses Comprehension Gulf)**

Users can annotate observations directly on individual documents and LLM outputs while inspecting them, without switching tools. Notes are stored as tuples of (operation ID, attribute name, free-text comment, optional color-coded category tag). They persist across pipeline runs and are searchable/filterable in a sidebar. Color-coding mirrors qualitative analysis tools like MAXQDA. Notes serve as the primary input to the prompt refinement feature.

**Feature B — LLM-Assisted Prompt Refinement (addresses Specification Gulf)**

When users click "Improve" on an operation card, a dialog opens showing the current prompt, all relevant in-situ notes, and a sample of documents. The system sends this context to `gpt-4o-mini` along with basic prompt engineering guidelines (be clear, unambiguous, provide few-shot examples). The LLM returns a revised prompt with structured `<prompt>` and `<schema>` tags. The UI shows a diff visualization between the old and new prompt. Users can: accept directly, edit manually, or instruct the AI to revise further. All revisions are tracked in a **tree structure** (not a linear history), so users can navigate back to any prior version and branch from it. This is a non-chat UI that maintains conversation context in the background while presenting only the latest suggestion.

**Feature C — LLM-Assisted Operation Decomposition (addresses Generalization Gulf)**

After every pipeline run, DocWrangler automatically samples five output documents and submits them to `gpt-4o-mini` with an LLM-as-judge prompt to assess whether outputs meet criteria (returning True/False). For failed assessments, a second LLM call generates specific failure reasons. These appear as **non-intrusive notifications** rather than blocking alerts. If the user accepts the decomposition suggestion, DocWrangler invokes DocETL's accuracy optimizer, which generates and tests multiple candidate decomposed pipeline plans (also using LLM-as-judge evaluation) and returns the highest-accuracy plan. The optimization logs stream to the UI in real-time.

### Supporting UX Decisions

- **Sampling before full runs:** Users can execute on a configurable sample (e.g., 10 documents) before committing to the full corpus, addressing the premature commitment problem.
- **Output caching:** Results are cached by document ID and operation sequence hash; only modified operations and downstream steps are recomputed on subsequent runs.
- **Auto-generated column visualizations:** Numerical attributes get 7-bin histograms; booleans get 2-bin bar charts; categorical strings (fewer than 50% unique values) get bar charts of top 7 values; non-categorical strings get word or character count distributions.
- **Per-document prompt viewer:** Hovering over a row reveals the exact expanded Jinja prompt sent to the LLM for that document, supporting verification of template correctness.
- **Prompt revision tree:** Visualized as an interactive diagram showing branching prompt versions, accessible via the "Add Feedback" button.
- **AI assistant chatbot:** A context-aware general-purpose assistant for syntax help, Jinja templating, and workflow guidance — integrated in-panel to avoid context switching to external tools like ChatGPT.
- **Output schema as "speed breaks":** The required output schema definition slowed users down enough to trigger meaningful reflection about their goals — an unintentional but beneficial design effect.

## 3. System Architecture

**Frontend:** Next.js with TypeScript, styled with TailwindCSS. Monaco Editor is used for operation editing (the same editor underlying VS Code). ReCharts (a React wrapper around D3) handles visualizations. WebSocket connections receive real-time streaming updates from the backend.

**Backend:** Python FastAPI. The backend compiles the visual pipeline representation into DocETL's execution format and processes documents in parallel. WebSockets are used for streaming.

**Storage:** Pipeline definitions, user notes, and datasets are stored on disk (local deployment) or S3 (public deployment). User notes are additionally cached in browser storage for fast querying. Operation outputs are cached using Python's `diskcache` library, keyed by document ID and operation sequence hash.

**Execution Engine:** DocETL, which provides map, filter, reduce, resolve, unnest, split, gather, and parallel-map operators. Operators use Jinja templates for prompts, and each operation enriches documents with new key-value pairs passed to downstream operations.

**AI-Assisted Features:** All use `gpt-4o-mini`. The prompt refinement AI receives: current prompt, output schema, a sample of documents, in-situ notes with corresponding documents, and prompt engineering guidelines. The decomposition judge samples five documents and runs a single batch assessment.

**Context Window Management:** A dynamic truncation strategy handles the 128,000-token context limit. Token count is calculated using `gpt-tokenizer` before each call. If the limit is exceeded, middle content is removed from sample documents in the first message only (preserving beginnings and endings, since introductions contain metadata and conclusions summarize content), replaced with ellipsis. Subsequent conversation history is preserved intact.

**Deployment:** Containerized with Docker for open-source self-hosting. The public version runs on Modal Labs' cloud platform. Users supply their own LLM API keys.

## 4. User Study Results and Evaluation

The evaluation used two complementary methods.

### Think-Aloud Study (n=10)

**Participants:** Recruited from the DocETL Discord community. Backgrounds included data science, ML engineering, data visualization, operations management, medicine, and graduate research. Four had prior DocETL experience. Two brought their own datasets (safety records and privacy policies). Sessions were one hour via Zoom, with 15 minutes of onboarding and 40+ minutes of task completion.

**Datasets and Tasks:** Medical transcripts (six participants), presidential debates (two), safety records (one), privacy policies (one). Tasks ranged from structured extraction (patient demographics) to open-ended analysis (identifying evaded debate questions, analyzing patient discomfort relative to illness type).

**Quantitative Reception:** All 10 participants found the IDE useful. Ease-of-use Likert ratings: median = 6.5, mode = 7 on a 7-point scale; 80% rated 6 or 7; no ratings below 5.

**Activity Distribution:** Engagement was balanced across Initialize, Inspect, and Improve phases, with frequent transitions between them rather than strictly sequential progression.

**Key Behavioral Findings:**

Finding 1 — Users manipulate semantic operations to aid validation. Rather than accepting raw LLM outputs, participants repurposed operations as validation scaffolding:
- Adding "reasoning" attributes to output schemas to force the LLM to explain itself (P1, P8)
- Creating summary map operations on extracted attributes to reduce manual review volume (P6)
- Adding boolean indicator attributes (e.g., `has_GDPR_mention`) to enable histogram-based filtering (P8)
- Converting open-ended tasks to classification problems: 6 of 10 participants independently arrived at this strategy. P1 explicitly described "treating the LM like a classifier." The evolution from binary (uninformative: 100% "true") to 5-point Likert scale (more variation, debuggable) was a common pattern.
- Adding taxonomy-structured categorical attributes to enable systematic error spotting by category (P10 with fallacy types, P9 with hierarchical symptom taxonomy).

Finding 2 — Users engage in "opportunistic realignment." Unlike traditional data science where exploratory data analysis precedes pipeline construction, all 10 participants skipped manual document review and immediately wrote map operations. They iterated by reacting to LLM outputs:
- When LLMs misunderstood intent, users reframed their goals (P4's symptom deduplication problem, P6's verbosity problem)
- Some redistributed work between LLM and code-based operators (P2, P4 replaced a semantic reduce with a code-based string-matching reduce to preserve symptom specificity)
- When LLMs surfaced unexpected but useful outputs, users shifted analytical goals to incorporate them (P9 adding medical history extraction after the LLM surfaced it serendipitously)
- P9 coined the term "prompt rubber ducking" to describe how LLM interaction clarified what questions were worth asking

Finding 3 — Operation Decomposition served dual purposes. Although designed for the generalization gulf, participants also used decomposition insights to navigate the comprehension gulf — understanding how the LLM interpreted their data. All 10 reviewed decomposition suggestions at least once; 5 applied them automatically. Users with higher confidence preferred to use decomposition insights as inspiration for manual rewrites rather than accepting automatic changes.

Finding 4 — Participants identified tooling gaps:
- **Bottom-up validation:** Users preferred discovering evaluation criteria through hands-on review rather than specifying rubrics upfront (top-down). They found automated LLM-as-judge viable in principle but impractical when goals shift frequently.
- **Provenance tracing:** Participants wanted outputs linked to specific source text spans with highlights, not just keyword search. The limitation that LLMs can hallucinate even when the term appears in the document (P9: "muscle aches" extracted as patient symptom but appeared only in the doctor's question) makes span-level provenance important.
- **Operation-specific visualizations:** The histogram/bar chart defaults were insufficient. Requests included: LLM-generated custom charts (P7), distribution change tracking across iterations (P4).

### Public Deployment Analysis (1,500+ pipeline executions over two months)

**Domains:** Legal (contract clause extraction), healthcare (clinical case studies), finance (invoice parsing), education (test generation from textbooks), customer feedback, government documents, media/news analysis. Nine languages represented.

**Task patterns:** Extraction was most common (>50% of pipelines). Classification ranked second. Most workflows followed: extract → classify → summarize. Business analysis pipelines were the most complex (up to 15+ operations). 75% of pipelines had two or fewer operations; 90% had three or fewer; 5% had more than five; some exceeded 30.

**Document types:** ~50% semi-structured with hierarchical sections; unstructured text (often PDF) was next most common.

**Model usage:** gpt-4o-mini (default) in 82% of pipelines; gpt-4o in 12%; Gemini in 17% (notably for PDF processing); Claude-3.5-sonnet in 9% (notably for classification); 18% used multiple models.

**Pipeline evolution:** Of pipelines with consecutive versions within 5-minute intervals: 53% grew more complex (added operations or upgraded models); 18% became simpler; 29% changed only prompts or schemas. Prompt evolution: 47% became more specific; 16% became simpler (following "prompt rubber ducking"); 37% had minor refinements.

**AI feature usage:** 150 instances of prompt refinement, 95 instances of AI chat. Notably, over half of prompt refinement uses involved no in-situ notes — users were using it to convert vague prompts into detailed specifications from the outset (e.g., transforming "Extract the information from the ledger" into a 10-line specification that noted the documents are scans of handwritten records). User frustration was visible in some notes (e.g., "MAP THEM ALL SYSTEMATICALLY!!!!!!!!" and "WHY IS THIS SO HARD?!").

## 5. Limitations

The authors explicitly identify the following:

**Sample bias in the study:** All 10 participants were tech-savvy and had prior LLM experience; most had programming backgrounds (though 3 had not heard of map-reduce). This may have made adaptation to the system easier than it would be for less technical users.

**Session duration:** Study sessions were 1-2 hours. Real document analysis spans days or weeks. Longitudinal behavior — how pipelines evolve over time, how teams collaborate, how mental models shift — was not observed.

**Deployment self-selection:** The public deployment requires users to supply their own LLM API keys, which filters toward technically capable and motivated users who discovered the tool through blog posts and technical talks. More experienced users also run DocWrangler on their own infrastructure, for which no telemetry exists.

**System-specificity of findings:** Behavioral findings come from one specific system. It is unclear how much of what was observed reflects fundamental aspects of human-LLM interaction versus artifacts of DocWrangler's specific design choices.

**Unresolved design tensions:** The paper acknowledges that "intent discovery" (figuring out what you want to ask) and "intent clarification" (expressing it precisely) are fundamentally different problems that DocWrangler treats with the same features, but they likely require different tools. The paper does not solve this — it identifies it as future work.

**No ground truth evaluation:** The paper does not report accuracy metrics or benchmark comparisons for pipeline outputs. The LLM-as-judge approach used for decomposition has known limitations (the referenced paper [85] specifically concerns limitations of LLM-as-judge for expert knowledge tasks).

**Data cleaning blind spot:** Users never created dedicated data cleaning operations, expecting LLMs to handle data quality implicitly. The LLM-pipeline blurs the traditional boundary between cleaning and analysis, and DocWrangler provides no specific support for this.

## 6. Relation to the Broader LLM Data Pipeline Field

DocWrangler sits at the intersection of several active research areas.

**Relation to semantic data processing systems (DocETL, LOTUS, Palimpzest, Palimpchat):** These systems provide the computational substrate — LLM-powered relational operators on unstructured data. DocWrangler is explicitly built on DocETL but frames itself as backend-agnostic. The key distinction is that prior systems optimize the "inner loop" (cost, accuracy given a fixed specification) while DocWrangler addresses the "outer loop" (how users discover and refine what they want to compute in the first place). This is a meaningful gap: LOTUS and DocETL can auto-optimize pipelines, but only once a well-specified task exists.

**Relation to prompt engineering tools (ChainForge, AI Chains, EvalLM):** Tools like ChainForge support interactive prompt experimentation, and AI Chains supports transparent chaining of LLM calls. DocWrangler differs in being data-processing-first rather than prompt-engineering-first, and in being oriented toward processing large document corpora (not single-input testing). The in-situ notes → prompt refinement loop is a specific contribution over general prompt engineering tools.

**Relation to LLM-assisted data analysis for structured data (Chat2Data, WaitGPT, Kazemitabaar et al.):** These tools generate SQL or pandas code via LLMs for structured data. DocWrangler argues these systems treat LLMs as code generators, not as semantic operators. The validation challenge is fundamentally different: code can be statically analyzed and tested, but LLM semantic operations are inherently uncertain and context-dependent. DocWrangler also emphasizes data-continuous inspection (the spreadsheet viewer is always visible alongside the pipeline), which code-centric tools deprioritize.

**Relation to task decomposition research (DSPy, crowdsourcing workflows):** DSPy and similar systems auto-compile declarative LLM pipelines, but they require well-specified evaluation metrics upfront. DocWrangler's decomposition feature is interactive and human-in-the-loop: it surfaces candidate decompositions for user review rather than fully automating the optimization. The study found users used decomposition suggestions even when they chose not to apply them automatically — using them as insight rather than automation.

**Relation to LLM-as-judge methodology (SPADE, MT-Bench):** DocWrangler applies LLM-as-judge for background accuracy checking and decomposition candidate selection. This is a novel application to the data pipeline context (prior LLM-as-judge work focused on evaluating chatbot responses, not data processing pipelines across large corpora).

**Relation to HCI and mixed-initiative systems:** The work draws heavily on Norman's gulfs framework, mixed-initiative interface principles (Horvitz 1999), predictive interaction (Heer et al.'s Wrangler), and creativity support tool theory. The "epistemic artifact" framing — where early pipeline iterations are exploratory objects to learn about data rather than production outputs — is a meaningful theoretical contribution that generalizes beyond DocWrangler.

**Broader implications:** The paper argues that semantic data processing represents a new paradigm for data systems that fundamentally changes the human role. Traditional data tools are "passive" executors of fixed specifications. Semantic data processing systems must be active collaborators in helping users discover what specifications to write. The authors position this as part of a broader shift described in the VLDB literature on how LLMs will disrupt data management. The "three gulfs" framework they introduce is presented as potentially generalizable beyond document processing to any human-AI collaborative system where "data" could be a single essay, a piece of software, or any artifact the AI processes.

---

**Summary assessment:** DocWrangler is a well-motivated system paper with a coherent theoretical framework, a practically deployed system, and a dual-method evaluation. Its strongest contributions are the behavioral findings from the think-aloud study (especially the classifier-transformation strategy and prompt rubber ducking) and the "three gulfs" conceptual model. Its weakest aspects are the lack of controlled accuracy comparisons, the small and self-selected study population, and the unresolved tension between intent discovery and intent clarification. The deployment data is particularly valuable as a rare source of ecological validity for an HCI systems paper.
