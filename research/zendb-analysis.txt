## ZenDB: Detailed Analysis

### 1. Problem Statement

The paper addresses a fundamental gap in data management: the inability to run ad-hoc analytical SQL queries over large collections of unstructured documents (PDFs, Word documents). The problem has three facets:

**The unstructured data problem.** Over 80% of enterprise data is unstructured and growing at 50%+ annually. Document collections — civic government agendas, scientific papers, legal notices, job descriptions — contain rich, queryable information but no existing system supports analytical queries over them.

**Failure of LLM-only approaches.** Feeding an entire document to GPT-4 and asking analytical queries fails for two reasons: (a) LLMs struggle with long contexts and complex multi-predicate aggregation tasks, causing accuracy problems; (b) sending entire documents to commercial API-based LLMs (token-in + token-out billing) is prohibitively expensive — on the order of $0.33–$0.98 per query per document.

**Failure of RAG-based approaches.** Retrieval-Augmented Generation reduces cost by retrieving only short text chunks near the query embedding, but it retrieves semantically isolated fragments that miss related content spread across multiple pages. In the paper's motivating example, RAG retrieves the first mention of "Capital Improvement Projects" but misses 20+ subsequent project entries in following pages. This yields very low recall (as low as 0.04 on the Civic dataset).

The central insight is that neither approach exploits the *semantic structure* that many document collections implicitly contain.

---

### 2. Key Technical Approach

The core idea is to detect and exploit the **template-based hierarchical structure** shared across documents in a collection. Documents created from the same template — e.g., all civic agenda reports from a county, or all VLDB papers — exhibit consistent visual formatting at corresponding semantic levels (font size, bold, centering, capitalization patterns mark headers at each nesting depth).

ZenDB's approach proceeds in three conceptually distinct phases:

**Phase 1: Extract Semantic Hierarchical Trees (SHTs).** Rather than treating documents as flat token sequences, ZenDB recovers a tree that mirrors the document's section/subsection hierarchy. It does this by clustering words into phrases by formatting features and then clustering phrases by *visual patterns* (a 7-feature vector: font size, font name, bold/italic type, all-caps, starts-with-number, starts-with-letter, centered). Clusters with content-level formatting are pruned using a small number of LLM calls; remaining clusters form the tree nodes. The algorithm provably recovers the correct tree if the document is *well-formatted* (siblings share the same visual pattern; all nodes of a given visual pattern share the same path-to-root visual-pattern sequence). Critically, for a collection sharing a common template, LLM calls are only needed for *one representative document per template*; subsequent documents are matched against the template purely by visual-pattern matching — no LLMs needed.

**Phase 2: Map user-defined schema to SHT nodes (Table Population).** Users declare tables using extended SQL DDL with natural-language descriptions but no attribute values. ZenDB uses LLM oracles to identify which SHT node "owns" a given table (the `table_node`) and which subnodes correspond to individual tuples. This is done once per template (one representative document) using LLMs; remaining documents in the same template cluster use rule-based matching. Attribute values remain NULL until query time (lazy population).

**Phase 3: Query execution leveraging SHTs.** A standard SQL query planner is adapted to minimize LLM invocations as the primary cost. This involves: (a) predicate pushdown and reordering using a cost metric that balances selectivity and per-tuple LLM call cost; (b) projection pull-up so attributes for discarded tuples are never materialized; (c) a *summary-based tree search* algorithm that navigates the SHT top-down to find the minimal text span relevant to a predicate or projection, using compact per-node summaries rather than full text spans.

### 3. System Architecture

**Document Ingestion (Section 3).** The pipeline uses `pdfplumber` for PDF-to-text conversion with formatting metadata. Words are grouped into phrases by identical formatting. Visual patterns cluster those phrases. `oracle_gen(D)` applies LLM calls only to sample phrases per cluster to distinguish headers from body text (97% accuracy at $0.37 total across 200 documents). `template_gen(tp, D)` matches subsequent documents to an already-known template purely by visual-pattern lookup.

**Data Model (Section 4).** Three table types coexist:
- *SHT Table*: One row per SHT node per document. Attributes include `doc_id`, `node_id`, `name` (header text), `granularity` (depth), `context` (full text span), `summary`, `size` (token count), `child_ids`, `ancestor_ids`, page range.
- *User-Defined DTables*: Declared via `CREATE TABLE … WITH DESCRIPTION`. Tuples are prepopulated (without attribute values) at schema time; attributes are materialized lazily at query time.
- *System Catalogs*: Table Catalog and Attribute Catalog store metadata including the `table_node`, `t_range` (granularity range of tuples), and a `multi_tuple` flag for when a leaf node contains multiple entity instances.

**Query Language (Section 4.2).** A SQL subset supporting `SELECT`, `FROM` (one or more DTables), `WHERE` with up to three predicates (`>`, `<`, `=`, `LIKE`, `IN`), `GROUP BY`, and standard aggregations. Cross-table joins are restricted to same-document (`doc_id`) equi-joins for now.

**Table Population (Section 5).** For one representative document per template, `table_oracle` and `tuple_oracle` LLM prompts walk the SHT top-down to identify the table node and tuple nodes. For remaining same-template documents, two deterministic rules propagate this mapping: Rule 1 matches `table_node` by granularity + header-text similarity; Rule 2 checks whether child nodes of the inferred `table_node` fall within the known `t_range`. A `multi_tuple` flag handles leaf nodes containing multiple entities.

**Query Engine (Section 6).** The logical planner applies classic Hellerstein-Stonebraker predicate migration extended to treat LLM call cost as the expensive predicate cost. The physical planner implements:
- `tree_evaluate(SHT, tuple, e)` (Algorithm 2): top-down SHT traversal guided by `search_oracle`, which checks if a node's summary contains information relevant to expression `e`. Candidate nodes passing `search_oracle` are then evaluated with `evaluate_oracle` (predicates) or `extract_oracle` (projections).
- `tree_evaluate_multi_tuple` (Algorithm 3): for `multi_tuple=true`, traverses to a fixed stop-granularity then calls `multi_tuple_oracle` to extract all matching tuples from each candidate node at once.
- Node summary construction (offline): anchor phrases + ancestor header phrases + extractive summary via NLTK + (at query time) top-1 sentence by cosine similarity to the query expression.
- Provenance tracking: text span arrays are propagated through operators to allow result verification.

### 4. Evaluation Results

**Datasets.** Three real-world collections:
- Publications: 100 scientific papers (avg 11.5 pages, 13,230 tokens), 20 queries from a UC Irvine personal data management systematic review.
- Civic Agenda: 41 reports from City of Malibu (avg 8.7 pages, 3,185 tokens), queries from Big Local News collaborators.
- Notice of Violations: 80 US DOT hazardous materials notices (avg 7.1 pages, 3,719 tokens).

**Baselines.** GPT_single (one LLM call per predicate+projection, full doc), GPT_merge (all predicates in one prompt, full doc), RAG_seq (LlamaIndex sequential chunking, 128-token chunks), RAG_tree (LlamaIndex hierarchical summarization). All use GPT-4-32k.

**Key quantitative results (Table 2 — averages across all datasets per query per document):**

| Strategy | Precision | Recall | Cost ($/query/doc) | Latency (s) |
|---|---|---|---|---|
| GPT_single | 0.63 avg | 0.53 avg | $0.54 avg | ~12s |
| GPT_merge | 0.54 avg | 0.52 avg | $0.40 avg | ~8.4s |
| RAG_seq | 0.33 avg | 0.30 avg | $0.017 avg | ~3.4s |
| RAG_tree | 0.30 avg | 0.20 avg | $0.043 avg | ~6.7s |
| **ZenDB** | **0.73 avg** | **0.70 avg** | **$0.027 avg** | ~4.5s |

**Against GPT-only baselines:** ZenDB achieves comparable or better accuracy (up to 28% precision, 39% recall improvement on the Civic dataset) at 4–29× lower cost. The Civic dataset most dramatically shows ZenDB's advantage because its complex multi-page structure completely overwhelms vanilla LLM context handling.

**Against RAG baselines:** ZenDB improves precision by up to 61% and recall by up to 80% (Civic dataset: ZenDB recall = 0.84 vs. RAG_seq recall = 0.13), at marginally higher cost than RAG_seq. RAG_tree has higher cost than ZenDB with worse accuracy because it uses expensive recursive summarization while still chunking leaves at fixed granularity.

**Data preparation cost (Tables 6–7):** SHT construction costs are minimal: $0.048 for 100 publications, $0.005 for civic and violation datasets. Table population via GPT-3.5-Turbo adds $0.048, $0.005, and $0.005 respectively. False negative rate on table/tuple boundary detection is 0% across all datasets.

**Ablation study (Figure 11):** Removing the dynamic (query-time) summary component hurts accuracy most. Removing node/ancestor names hurts moderately. Removing the extractive summary has the smallest effect. Dynamic summaries also reduce cost by focusing LLM attention on the most relevant sentence.

**ZenDB-light (GPT-3.5-turbo for query execution):** Only 7% precision drop and 3% recall drop compared to the GPT-4 version, at ~100× lower cost. ZenDB-light can execute 3,500–8,000 queries with 2 predicates and 1 projection per document for $1, establishing practical deployability.

### 5. Limitations

Several limitations are explicitly stated or implied:

**Template dependency.** The entire architecture depends on documents being "templatized" — following shared visual formatting conventions. The paper explicitly scopes future work to handle the case where templates are absent or very noisy. Collections of truly heterogeneous documents with no consistent formatting would require a fundamentally different structure-extraction approach.

**Well-formattedness assumption.** The correctness proof for SHT construction requires that siblings share a visual pattern and that all nodes of the same visual pattern follow identical paths to the root. When documents deviate from this (e.g., inconsistent subsection formatting across sections), the algorithm falls back on heuristics without guarantees.

**Join restriction.** Joins are restricted to within-document equi-joins on `doc_id`. Cross-document joins (e.g., "find projects mentioned in both this report and that one") are left for future work.

**Aggregation gap.** The evaluation omits aggregate queries from the performance benchmarks, noting that aggregate correctness fully depends on the accuracy of the tuple-level extraction underneath — a reasonable simplification but one that doesn't measure end-to-end aggregate query accuracy.

**LLM inconsistency.** The paper acknowledges that the LLM may return inconsistent results: e.g., extracting an attribute value of "B" but evaluating the predicate `attr = 'A'` as true. Reconciling LLM inconsistencies in query semantics is explicitly deferred as future work.

**Multi-tuple leaf nodes.** When `multi_tuple=true`, ZenDB delegates entirely to a single `multi_tuple_oracle` prompt over a potentially large text span, losing the benefit of fine-grained SHT navigation. This is the fallback for documents whose internal tuple granularity is below the SHT resolution.

**Images/figures.** Images within documents are treated as opaque "special words" and are not analyzed for content. Document types where key information resides in figures or tables (e.g., financial reports) are out of scope.

**PDF extraction dependency.** Correct visual pattern extraction depends on `pdfplumber` successfully parsing font metadata from the PDF. PDFs that are scanned images or that use non-standard encoding may produce degraded or absent formatting metadata.

### 6. Relation to the Broader Field

ZenDB sits at the intersection of several active research areas:

**Document AI and structured extraction.** Commercial systems like Google DocumentAI and Azure Document Intelligence perform upfront ETL to convert unstructured documents into structured tables. ZenDB argues — and shows empirically — that upfront full-document LLM extraction is expensive and error-prone for complex documents; lazy, query-driven extraction focused on specific SHT nodes is both cheaper and more accurate.

**RAG.** RAG-based retrieval (Lewis et al. 2020, LlamaIndex, RAPTOR) improves on vanilla LLMs by retrieving relevant text fragments. ZenDB's fundamental critique is that fixed-granularity chunk retrieval by embedding similarity ignores hierarchical semantic structure — it retrieves the wrong granularity and misses related content scattered across a document. ZenDB replaces embedding-similarity chunk retrieval with structure-aware tree search, yielding dramatically better recall on complex documents.

**Multi-modal and text-native databases.** Systems like ThalamusDB, Symphony, WannaDB, and the "neural databases" line of work (Thorne et al.) apply LLMs to full documents for SQL-like querying. ZenDB distinguishes itself by explicitly exploiting template structure, enabling cost and accuracy advantages that full-document LLM approaches cannot achieve.

**Evaporate / schema inference.** Evaporate (Arora et al., VLDB 2023) uses LLMs to infer schemas and generate extraction rules over heterogeneous data lakes. ZenDB is complementary: it assumes more homogeneous templatized collections, uses the SHT as structure rather than flat extraction rules, and operates lazily (attributes materialized at query time rather than upfront).

**Classical DB query optimization.** ZenDB applies predicate pushdown, projection pull-up, and join ordering — classical techniques — but redefines the cost model so that LLM invocation cost (tokens × price) replaces I/O cost. This is a clean and practical adaptation of standard query optimization principles to the LLM-as-UDF setting, consistent with recent work on expensive predicate reordering (Hellerstein & Stonebraker 1993, revisited).

**Semi-structured data querying.** XQuery, XPath, and XML/JSON database extensions query explicit hierarchies. SHTs provide an analogous hierarchical index, but critically the hierarchy is *implicit* in visual formatting rather than explicit in document encoding — making automatic extraction the key technical challenge that ZenDB solves.

**Provenance.** ZenDB tracks text-span provenance for all query answers, aligning with the classical data provenance literature (Glavic et al.) and addressing a practical trust/auditability requirement for journalism and legal use cases.

In sum, ZenDB occupies a novel position: it is the first system to extract and exploit *semantic hierarchical structure from visual formatting metadata* in document collections as the organizing principle for cost-optimized, accurate SQL query execution with LLMs. The approach is practically grounded (real journalism collaborators, real datasets, real cost measurements) and achieves what neither purely retrieval-based nor purely LLM-based approaches can — high recall and high precision at low cost, specifically by matching the granularity of LLM attention to the semantic grain of the query.
