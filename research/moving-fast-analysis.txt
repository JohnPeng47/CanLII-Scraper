## Detailed Analysis: "Moving Fast With Broken Data" (arXiv 2303.06094)

**Authors:** Shreya Shankar (UC Berkeley / Meta intern), Labib Fawaz (Meta), Karl Gyllstrom (Meta), Aditya G. Parameswaran (UC Berkeley). Published March 10, 2023.

---

### 1. Problem Statement

The paper addresses **automatic data validation for continually-retrained production ML pipelines**, specifically the challenge of detecting when an incoming partition of training data is corrupted enough to warrant blocking model retraining before downstream accuracy degrades.

The industrial context is Meta (Facebook/Instagram) at scale:

- Data partitions can reach **several petabytes**, with **tens of thousands of features** per partition.
- Models are retrained continuously (every few hours to days) on the latest partitions. At this cadence, engineering bugs that corrupt features are nearly inevitable—especially because, at many organizations, feature generation pipelines are decoupled from model serving pipelines.
- The core tension is a **blocking dilemma**: blocking retraining too often leaves stale model snapshots in production; blocking too rarely allows corrupted models into production. The problem is compounded because the hold-out validation set used in model validation is typically drawn from the same corrupted partition, meaning a retrained corrupt model still passes model validation.
- A subtler cascading failure mode: once a bug is fixed, models previously retrained on the corrupted partition will themselves be corrupted, producing a cycle of degraded performance that is hard to recover from.

Prior work failed on three axes:
1. **Excessive manual tuning** (Schelter et al.): requiring engineers to enumerate and tune constraints per feature at scale of tens of thousands of features is operationally unsustainable.
2. **Too coarse-grained** (Breck et al. / TFX): schema validation (type checks, loose bounds) is necessary but insufficient.
3. **Too many false positives** (most distribution-shift methods): comparing a partition only to the immediately prior partition, or a flat aggregate of all historical data, fails to account for expected temporal patterns such as weekday/weekend cycles, Black Friday, or Prime Day spikes. These expected anomalies generate alert fatigue, causing engineers to silence or ignore the system entirely.

The formal problem: given a timestamped dataset D = {D₁, D₂, ..., Dₜ} with features F₁...Fₙ, define a data validation function f(Dₜ | D₁,...,Dₜ₋₁) → ℝ that scores the likelihood of corruption of partition Dₜ. A partition Dᵢ is labeled corrupted (yᵢ = 1) if a model retrained on it experiences a performance drop at timestamp i+1.

### 2. Key Technical Approach: Partition Summarization (PS)

**Partition Summarization (PS)** is the paper's central organizing framework. Instead of operating on raw petabyte-scale partitions, the system:

1. Computes statistical summaries Q for each feature Fⱼ across every partition Dᵢ (storing these in a summary store).
2. Compares a new partition's summary to multiple historical summaries to determine whether it is a true anomaly.

The key insight is to compare Monday's partition not just to Sunday, but to all historical Mondays (and all nearby days), capturing weekly periodicity. This is more sophisticated than comparing only to t-1 or to a flat aggregate of all prior data.

**Rolling normalization:** For each feature Fᵢ and statistic Q, the rolling average over the last k=7 days is computed. The normalized deviation can be expressed either as:
- **Percent difference (PD):** (Q(Fᵢ, t) − Q̄(Fᵢ, t)) / Q̄(Fᵢ, t)
- **z-score:** (Q(Fᵢ, t) − Q̄(Fᵢ, t)) / σ([Q(Fᵢ, t−1), ..., Q(Fᵢ, t−k)])

The aggregate score f(t) is the mean of normalized deviations across all features. An alert fires when f(t) exceeds an automatically computed outlier threshold (e.g., 95th percentile of historical f values), removing the need to manually set per-feature thresholds.

**Three adapted PS methods** (existing approaches adapted to the PS framework):

- **δ-Completeness Drop (f_C):** Scores time t based on the number of features whose completeness (fraction of non-null values) dropped more than δ from their rolling 7-day average, weighted by that feature's typical completeness. High f_C indicates several normally-complete features are now mostly null.
- **z-Score Anomaly Detection (f_z):** For a chosen scalar statistic Q (completeness found to work best), scores t based on the fraction of features with z-score ≥ τ from their rolling 7-day distribution. Features with z-scores below τ are zeroed to filter out noise; only the most anomalous features drive the score.
- **Two-Sample Statistical Tests (f_twosamp):** Computes eCDFs (99 percentiles) per feature and measures distributional shifts using KS (max L∞ deviation), Wasserstein-1 (total L₁ area between eCDFs), or DTS (Wasserstein-1 weighted by variance). Converts to p-values via bootstrapping; scores t as the fraction of features with p-value ≤ α=0.05.

None of these adapted methods alone met the precision requirements for Meta's pipelines.

### 3. System Design

#### Architecture

- **Data warehouse** stores raw partitions (written in PrestoSQL / Presto).
- Upon arrival of a new partition, a **PS job** is launched that computes both ML model performance metrics and summary statistics (mean, standard deviation, minimum, maximum, completeness, eCDFs, frequent values, approximate unique-value counts via sketches) for every feature. These are written to a **summary store**.
- All data validation methods read from the same summary store; they do not operate on raw data.
- Methods are implemented in **Python, Pandas, and scikit-learn**.

#### gate — The Primary Method

gate (the paper's main contribution) adds three components on top of the PS framework to achieve both high precision and recall:

**Step 1 — Decorrelation (Inter-feature validation):**
The key insight is that correlated features should be treated as a group: if a single engineering bug corrupts one feature, its correlated siblings also degrade, making the signal stronger. Conversely, monitoring features independently inflates false positives because many features share variance.

- Clustering is applied to **partition summaries** (not raw data, which would be computationally infeasible at petabyte scale).
- For each of the 6 summary statistics, a **covariance matrix** across features is computed from the summary table.
- **PCA** is run on each covariance matrix to determine the number of components vᵢ explaining 95% of variance; the number of clusters |G| = max(v₁,...,v₆).
- The sum of absolute covariance matrices forms a **graph adjacency matrix** (features = nodes, edge weight = correlation).
- **Spectral clustering** partitions this graph into cluster assignments Gₜ. Spectral clustering is chosen because it handles non-convex groups and operates on the graph of features (size n×n, not governed by the tuple count), keeping runtime stable over time as more partitions arrive.
- Clustering uses ~1 month of historical data to avoid data leakage into future partitions.

**Step 2 — Anomaly Matrix Creation (Intra-feature validation):**
- For each partition Dᵢ, six statistics are computed per feature: (1) completeness, (2) mean, (3) standard deviation, (4) number of unique values (approximated via sketches), (5) top frequency (most frequent value count / total count), (6) Wasserstein-1 distance between consecutive partitions' eCDFs.
- Each statistic is converted to a **z-score** relative to a 7-day rolling window.
- z-scores are **averaged within each cluster** from Step 1, yielding a cluster-level anomaly vector x(t) ∈ ℝ^(6v) for each timestamp.
- These vectors are stacked into anomaly matrix X(t) ∈ ℝ^(t × 6v), where rows are timestamps and columns are (cluster, statistic) combinations.

**Step 3 — Alert Generation (Temporal validation):**
- Given X(t), an alert is generated using a **k-nearest-neighbor** comparison: the t-th row x(t) is compared (via Manhattan or Euclidean distance) to a fraction f of the closest non-anomalous preceding rows.
- The score f_gate(t) is the average distance to the ⌊f × t⌋ nearest non-anomalous neighbors. A partition is scored as anomalous if this distance exceeds a threshold computed from the historical distribution of f_gate values.
- Note that known-anomalous neighbors receive infinite distance (are excluded from the k-NN search), so the comparison is only against historically "clean" partitions.

**Step 4 — Feature Drill-Down (Debugging, optional):**
- When an alert fires, gate ranks clusters by their average z-scores and identifies the top features within those clusters with the largest individual z-scores by statistic.
- Engineers receive a ranked list of specific features and the statistics that are most anomalous, enabling fast debugging. The paper reports one practical instance where this identified an audio-related bug across >10,000-feature pipelines within seconds of inspection.

### 4. Evaluation Results

**Datasets:** Two Instagram ML pipelines (D1 and D2), each covering approximately 30 daily partitions from summer 2022. Both datasets have n ≥ 20,000 features (tens of thousands). The pipelines make binary-classification predictions (probability of a user clicking on a media recommendation).

**Ground truth labels:** Three failure types were unioned to produce yᵢ:
1. Cross-entropy loss increase ≥ threshold over 7-day rolling average.
2. Calibration error ≥ threshold.
3. Label shift (click rate drop) ≥ threshold.

Three **failure levels** (FL1, FL2, FL3) of increasing severity threshold were defined, so FL1 has the most labeled failures and FL3 the fewest. D1 failure rates: 0.33 (FL1), 0.23 (FL2), 0.17 (FL3). D2 failure rates: 0.59 (FL1), 0.47 (FL2), 0.44 (FL3).

**Metrics:** precision@0.9 (precision at the threshold yielding 90% recall — primary metric) and average precision (AP, secondary metric). Precision@0.9 is primary because a system that cannot recall most failures is not deployable; AP summarizes the full P-R curve shape.

**Baseline:** Redyuk et al. [48] k-NN method, which concatenates 7 statistics per feature into a vector and runs k-NN over historical vectors without temporal normalization.

**Key results:**

- On D1 (sparser failures, more representative of typical pipelines): gate gave **2.9× average improvement in precision@0.9** and **2.3× average improvement in AP** over the kNN baseline across failure levels.
- On D2 (denser failures): gate gave **1.3× improvement in precision@0.9** while achieving 0.9× the AP of the baseline (the baseline's AP was somewhat better in this high-failure-rate regime).
- The paper reports overall a **2.1× average improvement in precision** for gate over the baseline across the full case study.
- Wasserstein-1 two-sample test performed second best in precision@0.9 for severe failures (FL3) but was too computationally expensive for high-dimensional datasets; it cannot practically scale beyond ~10,000 features due to bootstrapping costs.
- The kNN baseline was the fastest method (no temporal normalization). The δ-completeness drop and z-score anomaly detection were similarly fast. gate ran in approximately **5 seconds** per partition (~50 seconds including the offline decorrelation step), making it operationally practical at O(10,000) features.
- Wasserstein-1 two-sample tests ran orders of magnitude slower than other methods and were impractical at high feature dimensionality.

**Practical on-call impact:** gate reduced alert fatigue. A concrete debugging example: an ML pipeline's performance had dropped and the root cause was unknown after several days of investigation. gate's cluster drill-down identified audio-related features as the most anomalous cluster (high Wasserstein-1 z-scores), pointing directly to a sound-related engineering bug.

### 5. Limitations

The paper is candid about several limitations:

**Cold-start problem:** gate requires approximately one week of historical partition summaries before it produces meaningful alerts. In the first week of deployment, nearest-neighbor comparisons are unreliable because there are too few neighbors. The recommendation is to use simpler methods (δ-completeness drop) in the first week and switch to gate thereafter.

**High failure rate regime:** When the failure rate is very high (D2, where >50% of partitions are labeled failures), gate's improvement over the baseline is less pronounced in AP terms, and the baseline (Redyuk et al.) actually achieves higher AP. The paper acknowledges that "most ML pipelines don't experience such a high failure rate."

**Feature type sensitivity:** gate works best with high-cardinality (real-valued, float, high-distinct-value integer) features. For pipelines composed primarily of binary or low-cardinality categorical features, simpler statistics (top-k frequencies, unique value counts) may suffice without the clustering overhead.

**Interpretability of the alert threshold:** While the threshold for f_gate is more interpretable than some alternatives (it can be estimated as max-allowed z-score × number of clusters v), the threshold is still computed from historical percentiles and may behave unexpectedly during distribution shifts that affect the entire history.

**Single-month evaluation window:** The case study covers only ~30 partitions per dataset from a single summertime period. Long-term drift, rare holidays, and seasonal changes extending beyond one month may reveal failure modes not captured in the evaluation.

**Privacy/legal constraints:** Feature and pipeline details cannot be disclosed, limiting reproducibility. The paper cannot describe what features the datasets actually contain.

**Temporal normalization sensitivity:** The k=7 rolling window is chosen for organizational (weekly on-call cycle) reasons, not empirically optimized. Different cadences (hourly partitions rather than daily) would require recalibration.

**Evaluation metric scope:** The paper acknowledges that precision@0.9 and AP may not be the only metrics of interest, and defers a broader discussion of alternate metrics (auROC, etc.) to a brief section at the end, noting that auROC is inappropriate given class imbalance.

**No ground truth for feature importance:** The decorrelation step uses correlation-based clustering rather than true feature importance (which would require SHAP or similar), because importance scores are unavailable for all model types (especially deep learning), change often as models retrain, and are computationally expensive to recompute.

### 6. Relation to the Broader Field

**Anomaly detection:** gate draws directly from the anomaly detection literature, particularly dissimilarity-based methods (k-NN outlier detection). However, unlike standard point-outlier detection (z-score, Median Absolute Deviation), the paper frames the problem as detecting subsequence-level anomalies — entire partitions as units of analysis. The paper distinguishes its approach from PCA-based high-dimensional anomaly detection because PCA produces uninterpretable low-rank components that cannot be debugged at the feature level.

**Data validation for ML (TFX, Deequ, DataSentinel, DaQL):** The dominant paradigm in this space (Breck et al. / TFX at Google; Schelter et al. / Deequ at Amazon; DataSentinel; DaQL) requires users to declaratively specify constraints (bounds, types, completeness thresholds). The paper's main departure is fully automatic constraint inference through the PS framework, removing the need for per-feature, per-pipeline manual tuning. Schema validation is treated as a prerequisite (not a replacement) since it exists at Meta already and is necessary but insufficient.

**Dataset shift / concept drift detection:** The literature on dataset shift (Rabanser et al. "Failing Loudly"; KS test-based drift detection) is closely related, but the paper argues convincingly that KS is inappropriate for the ML pipeline setting because it uses L∞ distance — a single large outlier can trigger it even when only a tiny fraction of tuples are affected, which would not actually degrade ML performance. L₁-based measures (Wasserstein-1) are more appropriate but computationally expensive. gate incorporates Wasserstein-1 as one of six statistics but avoids bootstrapping (so no p-values), making it fast.

**Data cleaning for ML:** Tools like ActiveClean, Boostclean, KATARA, and complaint-driven debugging aim to repair corrupted training data. The paper explicitly distinguishes its goal: not to clean all corrupted tuples (the pipelines already have high-performing models), but only to block retraining when corruption would cause a performance drop. This is a coarser but more computationally tractable goal.

**MLOps and production ML systems:** The paper connects to the growing literature on operationalizing ML (Shankar et al. "Operationalizing Machine Learning," Xin et al. on production ML pipeline analysis, Polyzotis et al. "Data Lifecycle Challenges"). A key empirical observation it reinforces is that feature generation pipelines are typically decoupled from model serving at large organizations, making data corruption between feature creation and training consumption a common and under-addressed failure mode.

**Partition-level summarization in databases:** The core PS idea borrows from query optimization and approximate query processing (materialized aggregates, synopses), adapting these techniques to the ML monitoring domain. The paper cites Zhang et al.'s BIRCH clustering on partitioned data as inspiration for performing clustering on summaries rather than raw data.

**Relation to Redyuk et al. (EDBT 2021):** This is the closest prior work — an automated k-NN approach to validating partitions of dynamically ingested data. The paper implements it as its baseline and identifies two critical flaws: (a) its normalization step rescales all statistics globally between 0 and 1 using the min/max across the entire history, causing features that did not change to have wildly different scaled values when any one feature has an outlier — a subtle but severe problem in high-dimensional ML datasets; (b) it treats all features as equally important, ignoring correlations and feature importance heterogeneity. gate's time-relative z-score normalization and clustering-based grouping directly address both flaws.

### Summary

"Moving Fast With Broken Data" makes a focused, practically-grounded contribution: a production-deployed framework (gate) for automatic ML data validation at Meta/Instagram scale. The Partition Summarization framework provides a clean abstraction for adapting any data quality metric to a temporally-aware, partition-level monitoring setting. gate's three-step pipeline — spectral clustering on covariance matrices of summaries, anomaly matrix construction from six z-scored statistics, and k-NN alert generation on cluster-averaged vectors — achieves 2.1× average precision improvement over the best prior automated baseline with only a few seconds of runtime per partition at O(10,000) features. Its primary practical value is reducing alert fatigue (false positives) while maintaining acceptable recall, which is the root cause of why prior data validation systems are silenced by engineers in production.
